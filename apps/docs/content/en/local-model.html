A third execution provider, and the first one that is not a service. Claude Code and Codex are programs that talk to somebody else's datacentre. Local talks to a model sitting in this machine's GPU — and almost everything that is different about it follows from that one fact.

The same agent, a different brain

A local session is not a chat window. It runs the Codex CLI against an Ollama server on this machine, through a provider J.A.R.V.I.S. configures for it. So it edits files, runs commands, writes a rollout, is followed by the conversation view, is governed by guardrails and can be run in a worktree — everything a Codex session does, with the model in your own card.

What you need

Ollama, running
Listening on http://127.0.0.1:11434 by default. The screen tells you the version it found, or says nothing answered.
The Codex CLI, installed
Local sessions run on it. It is not signed in to anything for this — no OpenAI account is used, read or required.
A model with tool support
The screen lists every installed model with its capabilities. A model without tools can talk but cannot edit a file or run a command, so it is not offered for sessions: it would produce an agent that narrates changes it never makes.

There is no account, and no allowance

The Accounts screen exists for a credentialed configuration directory with a five-hour window behind it. A local run reports rate_limits with every field null, because nothing meters a model you own. Modelling this as an account would put a quota dial on a card that can never move.

What actually limits a local model is physical, so that is what this screen reports instead.

Will it be fast? The two readings that decide

How much of the model is in VRAM
Read from Ollama's /api/ps, which reports the runner's total size against the part held on the GPU. Equal means every layer is offloaded. Anything less means the remainder is running on the CPU — and that is what a sudden collapse in tokens per second looks like from the inside. A 27B Q4 model that fits entirely in 24 GB runs at roughly 72 tok/s on an RTX 3090 Ti; the same model with layers spilled runs at a fraction of it.
Whether the card is being held back
The GPU panel reads power, temperature, clocks and — the reading that turns "it got slower" into something you can act on — why the clocks are down. Against a power limit, raising the limit is what buys speed. Against a thermal one, cooling is. They call for opposite responses, so they are never shown as one thing.

The context window, measured rather than assumed

The number the agent believes can be wrong

With no metadata for a local model, the Codex CLI warns and falls back to an invented context window — 258400 tokens, measured against a runner actually loaded at 65536. An agent that believes it has four times the context it has does not degrade gracefully; it fills the window and the server silently truncates the front of the conversation.

J.A.R.V.I.S. reads the effective window from the loaded runner and writes it into the configuration the session starts with, so the agent is told the truth. Where nothing is loaded there is nothing to measure, and the screen shows the server's configured default while saying that is what it is.

Server settings are not per session

Three things are read by Ollama once, when it starts, and apply to every client of it — not only to J.A.R.V.I.S.:

The default of 4096 is not a detail: an agent session on a 4096-token window truncates its own instructions. The screen can save these for your account, and says plainly that the running server keeps its old value until it restarts. A control that looked applied while the server ignored it would be the same class of untruth as an invented context window.

What a session may do

Sandbox
Read only, write inside the project, or full access to the machine. The default is to write inside the project: a local agent exists to change code, and a read-only default would make every session start by failing at the thing it is for. Full machine access is a choice you make, never one you inherit.
Approvals
When the agent stops to ask. Same values the Codex CLI uses, passed through verbatim.
Keep in VRAM
How long the weights stay loaded after the last request. Longer means the next prompt answers immediately instead of paying a reload of about ten seconds; shorter gives 17 GB back to the card sooner.
Preload on start
Loads the model when a session starts, on its own thread, so the first prompt is not the one that pays for the load. The session starts either way.

Why a configured provider and not --oss

The Codex CLI has an open-source mode — codex --oss --local-provider ollama — that runs an agent against a local model with no configuration at all. That was the first build here, and it works. It was dropped for one reason: it always talks to the runner's own default address, so the endpoint shown on this screen would have changed what J.A.R.V.I.S. reads and not what its sessions do. A person who moved their server to another port would have had a screen reading one machine while sessions talked to another.

One value in that configuration is not obvious

The wire protocol has to be named, and the obvious value is wrong: wire_api = "chat" is rejected outright by Codex 0.150.1 — the session dies on startup with "no longer supported", before its first prompt. "responses" is the value that works, and Ollama 0.33.2 answers POST /v1/responses. A full agent turn was run through this exact configuration before it shipped, and a test pins it, because the failure is total and invisible from the outside: the process starts and the agent never does.

Its own configuration root

Local sessions run with a CODEX_HOME this app owns, under its data directory. Two reasons, both concrete:

  • Correlation. A rollout is matched to a session by working directory and start time. A local session and a cloud Codex session started seconds apart in one project would write into the same tree and could each be handed the other's transcript — every turn, every token count and every searched sentence filed against the wrong session. Separate roots make that impossible rather than unlikely.
  • Configuration. The model, the sandbox policy and the measured context window have to be stated somewhere. Writing them into your own ~/.codex/config.toml would change how your Codex behaves outside this app. It is never read or modified.

In the live HUD

With the performance HUD open on a local session, the card appears beneath the token readings: power against the limit in force, temperature, utilisation, VRAM, and one line saying whether anything is holding the clocks down. It appears only for local sessions — beside a cloud agent's throughput a power meter would invite exactly the wrong conclusion, since this machine's GPU has nothing to do with how fast that answer arrives.

The context reading also changes shape there: with a measured window it is shown as a share of it, because 12k of 65k and 12k of 8k are different situations and a bare count cannot say which.
