Every capability the adapters declare, what each value means for you, and how it was established. Values are read from providers/claude.rs and providers/codex.rs.

These are data, not documentation

Each adapter returns this as a struct, and the interface renders from it. Nothing here is a boolean written into a component, which is why adding a third provider does not require touching a single React file. A test fails if the two adapters ever describe themselves identically.

What each value means

Session correlation

Deterministic
The provider accepts a session id we choose and writes its transcript under that name. The link is a fact we asserted. Claude Code: --session-id <uuid>.
FileWatch
The provider names its own files, so the adapter watches the directory and matches the one that appeared after this process started. A very good heuristic, and still a heuristic — two sessions started in the same second in the same folder is where it could be wrong. Reported honestly rather than dressed up.

Guardrail enforcement

PreExecution
Real enforcement. A refusal genuinely stops the command before it runs. Verified against Claude Code 2.1.240 by refusing a real force push and confirming the remote was untouched.
PreExecutionWhenTrusted
The same hook mechanism, but the provider will not run a hook until you have reviewed and trusted it in its own interface. J.A.R.V.I.S. writes the configuration at session start so it is there to be trusted. Until you do, that session is observed, not guarded, and the interface says so.

Briefing route

SystemPrompt
The brief is passed out of band, as an appended system prompt read from a file we own. Nothing is written into your repository, no turn is spent, and nothing appears in the terminal. Claude Code: --append-system-prompt-file.
OpeningMessage
No out-of-band route exists, so a brief could only arrive as the session's opening message — visible in the terminal and costing a turn. Codex 0.147.0: its --help lists no equivalent, and instructions arrive as the prompt argument or on stdin. Reported rather than papered over, because a person choosing a provider for an unattended run should know which of the two they are getting.

Session titles

Provider
It names its own sessions. Claude Code writes an ai-title line — present in 89 of the 124 transcripts on the machine this was verified against.
Derived
It states no title, so one is computed from what was said. Codex 0.147.0 is here; set_thread_title exists in its rollouts but as a tool definition inside the instructions rather than an event it emits — checked across every rollout on that machine.

Resume mechanism

Fork
--resume <id> --fork-session honours our own session id and writes a new transcript named for it — so the continuation is a session we can follow from the start. Verified on Claude Code 2.1.241.
AppendInPlace
codex resume <id> appends to the rollout it was given rather than creating one. A different shape, measured on 0.147.0, and the interface says so rather than pretending the two are the same.

Where the transcripts live

Claude Code
~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl
  event types  user · assistant · system · attachment · ai-title
                file-history-snapshot · file-history-delta · frame-link · queue-operation
  usage        assistant.message.usage — input_tokens, output_tokens,
                cache_creation_input_tokens, cache_read_input_tokens
  structure    messages form a DAG via parentUuid
  turn end     stop_reason: "end_turn"   ("tool_use" = still working)
  headless     -p --output-format stream-json --include-partial-messages

Codex
~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl
  envelope     {timestamp, ordinal, type, payload} — strictly ordered by ordinal
  types        session_meta · event_msg/* · response_item/* · turn_context · world_state
  usage        event_msg/token_count — carries official rate_limits
  turn end     event_msg/task_complete
  headless     codex exec --json

Live quota probes

ProviderProtocolCosts
Claude Code get_usage on the stream-json control channel No HTTP endpoint of ours, no credential read, no token spent, no transcript written.
Codex account/rateLimits/read on codex app-server

Both were also run against an empty configuration directory before the feature was built: both read the account in the directory they are pointed at, and both fail by saying so rather than returning the ambient account's numbers under the wrong name. That is kept as a permanent safety test — if it ever passes as Ok, the feature is misattributing allowances and must be turned off.
