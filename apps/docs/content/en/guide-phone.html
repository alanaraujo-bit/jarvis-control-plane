You started a run and went to make coffee. An agent hit a guardrail and is waiting. Pairing a phone means you can answer that from the kitchen instead of finding out forty minutes later.

What this is, in one sentence

A blind mailbox. The desktop pushes a summary of what needs a person; the phone reads it and queues an answer. The relay stores only a hash of each token, holds no copy of your work, and is off entirely until you pair a device.

  1. Read what gets sent, before you connect

    Settings → Phone states it up front rather than afterwards.

    SentNever sent
    That something is waiting, and what class of thingFile contents
    Which project and which session, by nameTerminal output
    What is running right nowConversation text
    The device name, so you know which machineYour code, your diffs, your credentials
  2. Pair

    A six-character code. Single use, valid for five minutes, with attempts counted. No account, no email, no password. Open the web app on the phone and enter the code.

  3. Check it worked

    The phone should show your machine by name, and what is running on it. If nothing appears, the desktop half is one background thread that logs and swallows every failure rather than interrupting you — so check the Phone section rather than waiting.

  4. Answer something from it

    When a guardrail holds an operation, it appears on the phone with what it is.

    Only one answer is available there

    Allow once. Guardrails offer four answers and three of them write a lasting policy — including Never allow. A phone has a small screen and a thumb, so it gets the one answer that expires with the thing it answers.

    Refusing is simply not approving: the guardrail already refuses by default, so the safe outcome needs no button at all.

Disconnecting

One control in Settings → Phone. It revokes the token, not just the local pairing.

This had to be fixed to mean what it says

Found by running it: clearing the local pairing left the mailbox standing, and a paired phone kept reading. A switch that leaves a live token working is worse than no switch at all.

Everything expires, and that is enforced on read

A serverless relay has no process to sweep in and delete things, so expiry is checked when a value is read — an expired value is never served even if nothing has cleaned it up. Commands expire far sooner than status snapshots, because a stale approval is worse than a stale status.

What you cannot do from a phone

Start a mission
Declined rather than overlooked. Starting one needs the same checks the desktop makes — including refusing an untrusted folder — and doing those correctly from a phone is its own piece of work rather than a button.
Read the conversation
By design. A relay holding a copy of the work would be the second store the session log exists to prevent.
Receive a push notification
Not built. It needs a developer account and is its own scope. The relay snapshot already carries what needs a person — the same question answered on a different screen. See What is not built.
One honest caveat about how it looks

The web app's logic is tested and its transport is proven end to end against real infrastructure — after pairing, the desktop published on its own and the mailbox came back carrying the real machine's hostname with nobody driving it.

But it has never been looked at on a phone-sized viewport. How it behaves is verified; how it looks is not.
