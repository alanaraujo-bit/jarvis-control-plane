Autonomy answers one question: how much does the agent decide on its own? Guardrails answer a different and narrower one — what it may never do regardless. Autonomy is the broader question, which is why Settings puts it above Guardrails: the fence only makes sense once you know how far the field goes.

Three profiles

Guided
The human stays close and the agent checks in often. Use it when the change is delicate, when you do not yet trust the shape of the task, or when you want to watch it think.
Autonomous
The agent handles what falls inside its remit and asks when something does not. The ordinary working mode, and the one that assumes you are at the keyboard.
Unattended
Designed to be left alone. Keep implementing, testing, fixing and verifying until the mission is done, genuinely blocked, or failed. Nobody is at the keyboard, and the product behaves as if that is true.
Unattended is a statement about you, not about the agent

Setting a mission to Unattended is you saying I am not going to watch this. The product takes that literally, and several behaviours change because of it — see below.

The chain: mission → project → global

Unset is genuinely unset — it is the absence of a row, not a stored default that looks the same. That is what lets a project-level change reach every mission that never expressed an opinion.

Guardrails resolve down the same chain, deliberately. Two settings that behave the same way are one thing to learn instead of two.

An audit found three values nobody could change

The product used them, showed them on screen, and gave no way to set them: the two upper levels of this chain, and the autopilot's turn budget — which the panel cheerfully rendered as turn 3 of 24 while 24 was a constant in the source. Terminal type size and scrollback were hard-coded too. All are now settings; none of them were new features.

What changes under Unattended

The autopilot takes the seat

After every turn it verifies the mission against its real criteria, then either sends the next instruction naming what does not pass yet, or stops with a reason. There are exactly three endings and keep going and hope is not one of them. See Inside the autopilot.

"Ask" becomes a refusal

A guardrail set to Always ask cannot ask anyone — you are not there. Parking the agent on a prompt nobody will answer wastes the whole run, so under Unattended an ask rule refuses instead, and the mission goes to Waiting with a reason you can read when you come back.

A driven session tells the guardrail it is driven, which is how the guard knows to do this.

Finished turns stop notifying you

Under the default budget an unattended run would otherwise produce twenty notifications while you were away by choice, and then a twenty-first when it actually stopped — the only one you asked for, at the bottom of a pile. So a driven session's finished turns are dropped.

Its questions are not. A driven agent that stops to ask is the one thing about an unattended run worth interrupting somebody for, because it cannot continue until they answer.

The agent is asked what it learned

At the end of a successful unattended run — once, and only then — the agent gets one narrow question about what would still matter next time, and its answer goes into the project's Brain. It is forbidden from touching anything while answering, and it is given a named escape hatch (NOTHING TO RECORD) that is expected to fire most of the time.

A manually completed mission is never asked, deliberately: typing a question into a terminal somebody is watching is a different conversation to interrupt.

An untrusted folder is refused up front

Claude Code asks whether you trust a folder the first time it opens one. A fresh worktree is always a brand-new folder, so an unattended run started there would hang forever on a question nobody is present to answer. Starting is refused instead, with the reason.

The turn budget

An unattended run stops after a fixed number of turns. The bounds are product decisions, not arbitrary limits:

  • Below 4, a run cannot finish anything real and every mission would end in Failed.
  • Above 100, run until done stops being a budget at all — which is exactly what the rule against consuming resources indefinitely exists to prevent.

Two details that matter more than they look. The bounds are enforced in the core, not only drawn in the slider: an out-of-range value is refused on the way in, and an out-of-range value already stored by an older build is clamped on the way out. And a run keeps the budget it started with — re-reading it each turn would let a change in Settings move the finish line under a run that is already going.

Where to set it

Globally in Settings → Autonomy; per project in the project's own Settings area; per mission on the mission itself. The panel is literally the same component in the global and project cases, which is why they cannot drift apart.
