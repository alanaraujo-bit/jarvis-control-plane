Four things are stopped, and none of them is stopped on engineering. Each is waiting on a purchase, a decision or an interactive sign-in that no amount of code can supply.

Why this page is public

Every one of these is visible from outside the product — the SmartScreen warning, the failing update check. Documenting them is cheaper than letting each person discover them and wonder whether the product is broken.

B1 — No code-signing certificate

Blocked on a purchase

What you see: Windows SmartScreen shows an unknown publisher warning the first time you install.

What is actually missing: an OV or EV Authenticode code-signing certificate. EV generally requires a hardware token or a cloud HSM. Nothing technical is missing — the build pipeline already has the shape for it, and applying one is configuration rather than code.

This is not the updater's key, and the two get confused constantly

The minisign keypair that proves an update came from us exists, works today, and verifies every download against a public key compiled into the binary before anything is installed. Update integrity is not affected by this blocker. See Distribution and updates.

B2 — Nowhere to publish updates yet (resolved)

Resolved in 0.10.0

The decision this was blocked on has been made: releases are published to the GitHub releases of this repository, and the updater's endpoint — releases/latest/download/latest.json — now points at something that exists. Check for updates reaches a real manifest and compares against a real version.

The manifest is written by hand as part of cutting a release, and its signature is the minisign signature of the installer it names. An installer whose signature does not verify against the public key compiled into the application is refused — that is the guarantee, and it is unchanged by where the files are hosted.

Kept here rather than deleted, because a blocker that was closed by a decision is worth being able to read: the alternative route considered — serving the manifest from the cloud project — would have put release artifacts behind a function built to pass small JSON around.

B6 — Signing in to additional accounts

Blocked on an interactive browser sign-in

What it blocks: one verification, not the feature.

Registering an account means creating a configuration directory and then signing in to it — and signing in means the provider's CLI opening a browser and a person completing an OAuth flow. No agent can do that on somebody's behalf, and the token-setup command is not a way around it: its first use needs the same interactive login.

What is built anyway: the registry, the configuration-directory plumbing, the quota model, the panel, the manual and automatic switch, and the Brain relay across a switch — all exercised against a live account plus alternate configuration directories, and validated in the release build in both languages and both themes under an isolated identifier.

What cannot run until it is done: one external-state verification — an account genuinely exhausting, work moving to a separately authenticated account, and the agent carrying on. See What is not built.

B-DOC1 — An unanswered remote-access request

Not a product blocker. Left for a person.

While this documentation was being built, an incoming AnyDesk remote session request appeared on the machine, from an ID nothing in this session recognised. It was left unanswered on purpose: accepting or rejecting a request for remote control of somebody's machine is not a decision to make on their behalf.

The window was minimised so it stopped covering the application being photographed. Minimising answers nothing, and the request is still exactly where it was.

It is recorded here and in the repository's own blockers file because a security prompt that nobody sees is worse than one that is merely unanswered.

Two blockers that resolved

Cloud provisioning
Resolved — and not by a change of plan. The command-line tools turned out to have been authenticated all along; the earlier status had been written from what was assumed rather than probed. One command would have settled it. The phone relay was built on it.
The installer build hanging
Resolved. The failure did not reproduce against a later pass.
One thing that is not a blocker but is worth knowing

The updater's private minisign key lives outside version control. Losing it means no existing installation can ever be updated again. It is a backup, not a blocker — but it is the failure with the least recoverable consequence in the whole project.
