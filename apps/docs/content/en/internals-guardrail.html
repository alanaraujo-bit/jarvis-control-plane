How a command gets stopped before it runs, and why the mechanism is shaped the way it is. Behavioural detail is on Guardrails; this page is the machinery.

The pipeline

Why the guard is a separate process

Because a session has exactly one writer

The guard runs as its own process and can never be the log's writer. It hands its decisions over the same way a provider hands over its transcript: by appending to a file that the single writer follows and turns into Approval frames.

This is the same two-process shape the whole architecture uses, and it is what keeps the ordering in the log a fact rather than an agreement between concurrent writers.

The provider invokes it — the same executable, with a flag — before every classified tool call. It reads the snapshot, classifies the command, and answers on stdout.

Why it is a snapshot, not a live read

guardrail-policy.json is written when the session starts, carrying the rules already resolved down the project → global → default chain and whether anybody is attended.

Changing a rule in Settings mid-session should not change what a running agent was told. A session that started under one policy finishes under it, which is also what makes the record readable afterwards: the decisions in the log are decisions under a policy you can inspect.

Why it fails open

No snapshot, malformed JSON, or a version it does not understand: it stays silent and the tool call proceeds.

Count the blast radius

This process runs before every tool call in every agent session. A guard that failed closed would turn any bug in itself — a missing file, a parse error, a version skew after an update — into an agent that cannot do anything at all, in every project, until somebody diagnoses it.

Failing open means a bug costs you the guardrail. Failing closed means a bug costs you the product.

The classifier

Heuristic matching over command text. It tokenises, respects quoting, and reads each program with its arguments. It is not a shell parser and does not pretend to be — a real shell parser would have to handle every expansion, substitution and alias, and would be a much larger surface to get subtly wrong.

The negative cases are the load-bearing ones

If the classifier flags things it should not, it becomes the first thing anyone switches off — and then it protects nothing. So these are pinned by tests:

✓ no match  git push --force-with-lease origin main
             refuses on its own when the remote moved — the safe spelling
✓ no match  echo "rm -rf /tmp/x"
             a string being printed, not a directory being deleted
✓ no match  npm publish --dry-run
✓ no match  cat .env.example
✓ no match  git switch main
             but `git switch --discard-changes main` does match

✗ matches   pnpm build && git push --force && npm publish
             each part of a chain is classified separately
Not flagged is not proven safe

A command the classifier does not flag failed to match a pattern. That is a different claim from this is harmless, and only one of them is true.

The identifiers are stable and never prose

The nine operations have fixed string identifiers — git.force-push, fs.recursive-delete, secrets.access and so on. They are used in storage, in the policy snapshot, and as the key suffix for the translated name. A name a user reads is never the thing a database stores.

Enforcement differs by provider, and the model says so

Claude Code runs the hook and a refusal genuinely stops the command. Codex has the same hook mechanism but will not run it until you have trusted it in Codex's own interface, so it is reported as PreExecutionWhenTrusted — observed, not guarded, until you do. See the provider matrix.

Where the gate is not a classifier at all

Inside Review, a discard names its operation directly rather than building a command string and asking the classifier what it just decided to do. It also writes no pending row: you are at the screen, so the question is asked and answered there rather than becoming something to resolve later.

Classifying a string you just constructed yourself is a round trip through a heuristic to recover information you already had.

Under Unattended

The snapshot carries whether the session is driven. A driven session with a rule set to ask gets a refusal, because parking the agent on a prompt nobody will answer wastes the whole run. The mission moves to Waiting with a reason.
