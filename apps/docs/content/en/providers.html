Two agent CLIs ship inside J.A.R.V.I.S. today: Claude Code and Codex. They are not interchangeable, and pretending otherwise would be the easiest way to make the interface lie.

A provider is an adapter, not a special case

Each provider is a Rust adapter behind one trait. The adapter's first job is to describe itself by returning a ProviderCapabilities struct — how sessions are correlated, where the conversation comes from, whether usage is official, whether a sensitive operation can be stopped, how a brief reaches it, where its sessions get their names.

The rule

Capabilities are data. They are never a boolean written into a component. A surface renders from what the adapter reports. Adding a third provider must not require touching a single React file — and if it did, the abstraction would already have failed.

This sounds like ordinary good practice until you see what it costs to break. The alternative is a component that says if (provider === "claude-code"), which is correct on the day it is written and silently wrong for every provider added afterwards. There is a test that fails if the two adapters ever describe themselves identically, because two providers reporting the same capabilities is far more likely to be a copy-paste than a truth.

The full matrix explains what each value means for you. The differences worth understanding now are these four.

Correlation: which transcript belongs to this session

When you start an agent, J.A.R.V.I.S. needs to know which JSONL file on disk is the one this process is writing. Getting that wrong attributes one agent's work to another.

Claude Code accepts --session-id <uuid> and writes its transcript under that name. The link is a fact we asserted, so it is Deterministic.

Codex names its own rollout files. The adapter watches the directory and matches on the file that appeared after this process started. That is a very good heuristic and it is still a heuristic, so it is reported as FileWatch rather than dressed up. Two Codex sessions started in the same second in the same folder is the case where it could be wrong, and saying so is cheaper than being confidently mistaken.

Guardrails: stopped, or only watched

Both CLIs have a pre-tool hook with the same wire shape. Claude Code runs it: a refusal genuinely stops the command before it executes, verified against 2.1.240 by refusing a real force push and confirming the remote was untouched.

Codex will not run a hook until you have reviewed and trusted it in Codex's own interface. J.A.R.V.I.S. writes the hook configuration at session start so it is there to be trusted, and until you do, that session is observed rather than guarded. That is exactly what PreExecutionWhenTrusted means, and the interface says it rather than showing you a shield that is not doing anything.

Briefing: how a project's memory reaches the agent

The Brain hands every agent a brief before it starts. Claude Code takes --append-system-prompt-file, so the brief is passed out of band: nothing is written into your repository, nothing is spent from a turn, and nothing appears in the terminal.

Codex 0.147.0 has no equivalent flag. A brief could only arrive as the session's opening message — visible, and costing a turn. The adapter reports OpeningMessage, and a person choosing a provider for an unattended run can see which of the two they are getting.

Measured, not read off a help page

The Claude Code briefing capability is pinned by an #[ignore]d test that starts a real agent through a real PTY and asks it for a codename that appears only in the brief. With the flag it answers; without it, it does not. A capability claimed from a --help listing is a claim about documentation, not about behaviour.

Titles: who names a session

Claude Code writes an ai-title line into its own transcript. Nothing was reading it, so every session in the database was untitled until History was built. It is present in 89 of the 124 transcripts on the machine this was verified against.

Codex states no title anywhere. set_thread_title exists in its rollouts, but as a tool definition inside the instructions rather than an event it emits — checked across every rollout on that machine. So its sessions get a Derived title, computed from what was said in them.

Both are watched the same way

The question that decided this whole design was whether one session can be simultaneously attached to a PTY and structurally observable. It can: both CLIs write structured JSONL transcripts to disk while running interactively.

// Claude Code
~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl
  events  user · assistant · system · attachment · ai-title · file-history-*
  usage   assistant.message.usage → input, output, cache_creation, cache_read
  shape   messages form a DAG via parentUuid

// Codex
~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl
  envelope {timestamp, ordinal, type, payload} — strictly ordered by ordinal
  types    session_meta · event_msg/* · response_item/* · turn_context · world_state
  usage    event_msg/token_count carries official rate_limits

This is why Conversation is real structured data rather than ANSI scraped out of a terminal. The tailer that reads these handles partial lines, UTF-8 sequences split across reads, truncation and CRLF — and it was validated by parsing every real transcript on the development machine: 79 files, 49,905 conversation items, 19,582 of them carrying official usage.

Where a provider is chosen

In a project's Sessions area, the + next to the tab strip offers a plain Shell and every agent the environment scan found on your machine. A provider whose executable is not on PATH is not offered, and the Environment section of Settings says what is missing.

In the source

providers/mod.rs is the trait and the capability model; providers/claude.rs and providers/codex.rs are the two adapters, each with the reasoning for its own values in comments; providers/tail.rs is the JSONL reader.
