A project is a real folder on your disk. Opening one does not copy it, index it, or write anything into it — J.A.R.V.I.S. asks Git what it is and remembers where it is.

The workspace: seven areas over one folder

Sessions Terminals and agents. The hero surface, and where the work happens. Files The tree, with Git-ignored entries dimmed, and Monaco behind it. Review What changed, attributed to the session that changed it. Preview The dev server an agent just started, opened from the address it printed. Worktrees Give an agent its own checkout. A worktree is a project. Brain What every agent starting here is told before it reads a file. Settings This project's own autonomy and guardrail rules.

Why these are not on the rail

Files, the editor, Review, Preview and Worktrees are project-scoped tools. Putting them on the rail would mean the rail either grows every time one ships, or has to answer "which project?" on every click.

So the rail stays six destinations and Settings, and the project header carries the rest. It is a rule about scanability more than about hierarchy: a navigation surface you cannot take in at a glance has stopped being navigation.

Path confinement is the security boundary

How file access is constrained

The webview only ever names paths relative to the project root, and the root itself is read from the database rather than accepted from the caller. Two independent checks follow: the request must contain no .., root or drive components, and then the resolved path is re-checked against the filesystem — so a symlink pointing out of the project is caught even though the request looked innocent.

Tested against a real temporary directory, including Windows verbatim (\\?\) paths and case folding, because those are exactly where a naive prefix check quietly passes something it should not.

Recents, and archiving

Projects you have opened stay in the list with their path and branch. Archiving one takes it out of the way without deleting anything — the sessions, missions and history that belong to it are all still there, and everything that links to it still resolves.

A worktree is a project

Opening a worktree opens it as a project, everywhere. Review inside a worktree compares against that worktree's branch, Files browses that checkout, and the Brain is the one that belongs to it. There is no worktree-specific code anywhere in the file, editor, Review or Git surfaces — which is the test of whether that decision was the right shape.

A bug that hid in this structure

Every project area was showing stale data. Areas are mounted once and hidden with CSS, so an effect keyed on the project id never fires again after the first project. Review's own comment claimed it re-read on every visit; it did not. Worth knowing if you are reading this code: mounted-and-hidden is not unmounted.

A session starts where it says it starts

If a project's folder has been moved or deleted, starting a session in it is refused. This was found by continuing a session into a deleted folder and watching a real agent open in the user's home directory instead — which is worse than an error, because the agent then happily works on the wrong files.
