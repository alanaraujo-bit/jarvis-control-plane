The point of an unattended run is that you leave. This guide is about setting it up so that leaving is a reasonable thing to do, and so that what you find when you come back is a result rather than a transcript to read.

The one thing to understand first

An unattended run finishes when real checks pass. If your mission has no criterion a machine can verify, the autopilot has nothing to steer by and will spend its whole budget guessing. The quality of the run is decided entirely by the criteria you write.

  1. Give the project a Brain first

    Nobody is there to correct a wrong assumption, so the assumptions have to be right at the start. Four sentences in Brain — what this is, the convention that matters, the trap, the vocabulary — are worth more here than anywhere else in the product.

  2. Consider a worktree

    A worktree gives the agent its own checkout on its own branch. It cannot dirty the tree you are reading and cannot fight you over a file.

    A fresh worktree is an untrusted folder

    Claude Code asks whether you trust a folder the first time it opens one. Nobody is there to answer, so starting is refused with that reason rather than hanging forever. Open the worktree once, answer the trust question, then start the run.

  3. Write criteria a machine can check

    Prefer Command over everything else — your test suite, a type check, a build, a lint. FileExists and FileContains are good for artefacts.

    Manual criteria are legitimate and the autopilot cannot satisfy them: a run whose remaining work is manual will correctly stop and wait for you. That is not a failure, but know it will happen.

    Mark the criteria that genuinely gate completion as required. A run stops when every required one holds.

  4. Set the guardrails you actually want

    Under Unattended, an Always ask rule becomes a refusal — nobody can answer, and parking the agent on a prompt would waste the run. So decide deliberately:

    • Leave it on Always ask if you would rather the run stop than do that thing.
    • Set Never allow if it must never happen, ever.
    • Set Allow only if you have genuinely thought about it.

    See Set up guardrails.

  5. Check the turn budget and the quota

    The budget is in Settings → Autonomy, between 4 and 100. A run keeps the budget it started with, so changing it later will not move the finish line under a run already going.

    Glance at the quota chips in the status bar. A run that starts on an account with twenty minutes left is a run that will stop for a reason that has nothing to do with your code.

  6. Set the mission to Unattended and start

    The autopilot takes the human's seat. After every turn it verifies the mission against the real criteria, then either sends the next instruction — naming what does not pass yet — or stops.

  7. Leave

    Finished turns will not notify you: under a default budget that would be twenty notifications while you are away by choice. Questions still will, because a driven agent that stops to ask cannot continue until somebody answers.

The three ways it ends

EndingWhat it meansWhat to do
Completed Every required criterion verified, with evidence attached. Read the evidence, then Review the diff.
Waiting · Blocked Something needs a person: a guardrail held an operation, or the agent hit something it cannot do. Read the reason — it is always stated — answer it, and restart.
Failed The turn budget ran out, or the same criteria kept failing. Read Activity for the turn-by-turn. Usually the criteria were wrong, not the agent.

There is deliberately no fourth ending. Keep going and hope is what a run does when the model gives it nowhere honest to stop.

What you will find when you come back

  • The mission, in one of the three states above, with evidence for every criterion it checked.
  • Activity, with every turn boundary, every verification, and the reason it stopped.
  • Review, with the diff, attributed to the session.
  • The Brain, possibly with one new entry — if the run completed, the agent was asked once what would still matter next time. Most of the time it declines, which is expected.
  • One notification, saying the run stopped and why.

Stopping a run early

Stopping does not kill the agent

Somebody taking over usually wants to type the next thing themselves, and killing the process would throw away its context. So the autopilot stands down and leaves you a live session at a prompt.

Why the autopilot never guesses that a turn ended

A quiet terminal means nothing — the agent might be thinking, or waiting on a network call. The stopping condition comes from the provider: Claude Code's stop_reason: "end_turn", Codex's event_msg/task_complete. Checked across 88 real transcripts: 664 turn boundaries, none of them ambiguous. See Inside the autopilot.
