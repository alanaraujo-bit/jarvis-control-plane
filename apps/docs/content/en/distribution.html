How the product reaches your machine, how it updates itself, and why neither operation can touch your data.

The installer

An NSIS installer built by Tauri, carrying its own identity: generated header and sidebar artwork drawn from the same signed-distance geometry as the application icon, and an English/Portuguese language selector matching the app's own locales, auto-selected from your OS language.

Per-user install

No administrator prompt, ever. Nothing is written outside your own profile, which is also why first run needs no elevation and why an update does not either.

Install footprint is 7.3 MB, measured on the real installer rather than estimated. Monaco accounts for 1.04 MB of that and is loaded on demand rather than at startup.

Single instance

Exactly one process owns the database and the session logs. A second launch hands off to the running window rather than opening beside it.

This is also why pnpm dev is silently swallowed while the installed copy is running — close the installed app first if you are working on the source.

Updating

The public key is compiled into the binary, not fetched. An update that fails verification is refused rather than applied — there is no path where an unverified artifact reaches your machine because a check timed out or a server said it was fine.

Two signing concerns, constantly confused

PurposeState
minisign keypair Proves an update came from us Working Generated locally, verifying today.
Authenticode certificate Stops Windows warning about an unknown publisher Blocked Needs a purchase. See Known blockers.

So: updates are cryptographically verified even though the installer is unsigned. Those are genuinely different guarantees, and conflating them is how people conclude either that the SmartScreen warning means updates are unsafe, or that a signed installer would make them safe.

For anyone building from source

The private minisign key lives in .keys/ and is gitignored. It must never be committed, and losing it means no existing installation can ever be updated again. Back it up somewhere that is not the machine that builds.

Your data cannot be touched by any of this

User data lives in %APPDATA%\dev.jarvis.desktop — the SQLite database and the per-session logs — entirely outside the installation directory.

  • An update replaces program files. It cannot reach projects, sessions, missions or history.
  • An uninstall removes the program and preserves the data. Reinstalling picks up exactly where you left off.
  • Removing it for real means deleting that folder yourself. See Where your data lives.

Schema changes are forward-only

Migrations are additive and never destructive, and a database written by a newer build is refused rather than opened. Rolling back a version cannot quietly corrupt history that the older build does not understand — it says it cannot read it, which is the recoverable failure.

What update checks do today

They report a failure, honestly. The updater is configured against a release location that is not yet published, so the check cannot succeed. That is a tracked blocker about where to publish rather than a bug in the updater — and reporting the failure is better than pretending to be up to date, which would leave you believing you had the latest build forever.

Platforms

Windows only, today. The core is Rust and the interface is a webview, so nothing in the architecture is Windows-specific — but the PTY host, the job-object containment, the toast integration and the installer all are, and none of those has been built or verified anywhere else. Claiming cross-platform support before that work exists would be the kind of claim this product's whole confidence model is against.
