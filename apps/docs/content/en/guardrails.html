You are going to leave an agent running while you do something else. Guardrails are what makes that a reasonable thing to do: nine classes of operation that get stopped and held for a decision before they execute.

The nine operations

OperationIdentifierWhat matches
Force pushgit.force-pushOverwriting a branch on a remote. Deliberately not --force-with-lease, which refuses when the remote moved.
Rewrite historygit.history-rewritereset --hard, rebase, filter-branch.
Delete a branchgit.branch-deleteDeleting a remote branch, or force-deleting a local one.
Throw away uncommitted workgit.discard-changesgit restore, checkout -- <file>, stash drop. The one thing Git keeps no copy of.
Delete a whole folderfs.recursive-deleterm -rf, Remove-Item -Recurse, git clean -f.
Read a credential filesecrets.access.env, private keys, .npmrc. Example files deliberately do not count.
Deploy to productiondeploy.productionvercel --prod, wrangler deploy, terraform apply.
Publish a packagepackage.publishnpm publish, cargo publish, docker push.
Run something downloadedremote.executecurl | sh, iex (iwr …).

Three answers, resolved down a chain

Each operation gets Always ask, Allow or Never allow, resolved project → global → default. The default is Ask. The chain is the same shape autonomy uses, on purpose.

Allow is silence, not permission

Allow means the guard does not object. It does not mean the operation was reviewed, and it does not mean it is safe. The distinction is written into the source next to the enum, because a reader who mistakes the two will design the next feature wrongly.

Where it can actually be enforced — and where it cannot

This is the part most tools would quietly overstate. The capability model reports the truth per situation instead:

SituationWhat happens
A verification command J.A.R.V.I.S. runs for a mission Real enforcement. We own the process.
A Claude Code session Real enforcement, through its pre-tool hook. Verified against 2.1.240: a force push was refused before it executed.
A Codex session Same hook mechanism, but Codex will not run it until you trust it in Codex's own interface. Reported as PreExecutionWhenTrusted — observed, not guarded, until you do.
A human typing in a terminal Nothing, deliberately. Guardrails govern agents. Your terminal is your terminal.

It fails open, and that is the right call

No policy snapshot, malformed JSON, or a version the guard does not understand: it stays silent and the tool call proceeds.

This looks backwards until you count. The guard process runs before every tool call in every agent session. A guard that failed closed would turn any bug in itself — a missing file, a parse error, a version skew after an update — into an agent that cannot do anything at all, in every project, until someone diagnoses it. Failing open means a bug costs you the guardrail; failing closed means a bug costs you the product.

How the classifier decides

It is heuristic matching over command text: it tokenises, respects quoting, and reads each program with its arguments. It is not a shell parser and does not pretend to be.

Read this sentence twice

A command the classifier does not flag has not been proven safe. It failed to match a pattern. Those are different claims, and only one of them is true.

The negative cases are the load-bearing ones. These must not match, or the guardrail becomes the first thing anyone switches off:

✓ no match  git push --force-with-lease origin main
             refuses on its own when the remote moved — the safe spelling

✓ no match  echo "rm -rf /tmp/x"
             a string being printed, not a directory being deleted

✓ no match  npm publish --dry-run
             publishes nothing

✓ no match  cat .env.example
             an example file is not a credential

✗ matches   pnpm build && git push --force && npm publish
             a chain is not one command; each part is classified

Where a discard is guarded and a stage is not

Inside Review, only discard is a guarded action. Staging and unstaging move the index and are reversible; asking about them would teach you to switch the guardrail off, and then the discard is unguarded too. Guarding everything is how you end up guarding nothing.

The gate there also names its operation rather than classifying a command string it just built itself, and it writes no pending row — you are at the screen, so the question is asked and answered there.

Under Unattended, "ask" refuses

A rule set to Ask cannot ask anyone during an unattended run. Rather than park the agent on a prompt nobody will answer, the guard refuses, and the mission moves to Waiting with a reason. The session tells the guard that it is driven, which is how the guard knows.

Verified against a real agent

Against real Claude Code 2.1.240: a force push was refused before it executed, and under Unattended an rm -rf was stopped with the directory still there afterwards. Separately, in the installed app: a mission whose acceptance criterion was npm publish had the check held rather than run, the approval was answered, and the mission left Waiting.

Inside the guardrail explains the mechanism — a separate process, a snapshot on disk, and decisions appended to a file the session follows.
