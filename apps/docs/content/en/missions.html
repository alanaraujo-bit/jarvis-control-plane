An agent that says Done! has told you what it believes. A mission is the mechanism for finding out whether it is true — and for noticing later when it stops being true.

What a mission is made of

A title and an intent
What you want. Ordinary prose, in your words.
Acceptance criteria
The conditions that decide whether it is finished. Each one is either required or not, and each one carries a verification — the thing that will actually be run.
An autonomy profile
How much the agent decides on its own. See Autonomy.
Evidence
What each check produced, kept — not a green tick, the actual outcome.

The four kinds of verification

KindWhat it doesChecked by
Command Runs a command and compares its exit code with the one you expected (0 unless you say otherwise). Runs in the project directory unless given another. J.A.R.V.I.S.
FileExists A path, relative to the project, must be there. J.A.R.V.I.S.
FileContains A path must be there and contain given text. J.A.R.V.I.S.
Manual Only a person can judge it. Recorded as such, so it is never mistaken for something that was actually checked. You
The point of the fourth one

Manual exists so that "the login screen looks right" can be a real criterion without pretending a machine verified it. Its evidence reads confirmed by you, never passed. A criterion that cannot be checked can only ever be claimed, and the product refuses to blur the two.

The seven states, and why two of them exist

Waiting and Blocked are the two that most tools do not have, and they are the reason this model is worth anything. A mission that cannot proceed has to say so. The alternatives are quietly declaring success, or burning your tokens forever — and both of those are things an agent will happily do if the model gives it nowhere else to go.

A blocked mission must also explain itself. Blocked with no reason is a state nobody can act on.

Completion is refused, not requested

You cannot mark a mission complete because you feel it is. The checks run; if a required criterion does not hold, completion is refused and the surface says which one and why.

Verified against the real product

A mission was created, completion was refused, verification was run, the work was done, verification passed, and the mission completed. Then the artifact was deleted from disk and the completion was revoked — because the evidence stopped holding.

Revocation is the part people do not expect

Evidence is re-checked, and a completion whose evidence no longer holds does not stay completed. This is what makes a mission different from a checkbox: a checkbox records that somebody once believed something. A mission records whether it is currently true.

Withdrawing a criterion is recorded, never deleted

If a criterion turns out to have been the wrong ask, you withdraw it — with a reason. It stays in the record, marked withdrawn, with your reason attached. Deleting it would let a mission be made to pass by removing the tests it failed, which is precisely the manoeuvre this whole model exists to prevent.

What evidence looks like

Every sentence J.A.R.V.I.S. writes as evidence is a translated string with the specifics substituted in, not English text stored in your database. A failing command reads, in Portuguese, exactly:

`exit 1` saiu com código 1, esperado 0

The command's own output — stdout, stderr, an OS error string — is stored with no translation code at all, deliberately. That is the tool speaking, not a sentence J.A.R.V.I.S. wrote, and translating it would be inventing words nobody said.

A bug worth knowing about

When evidence gained its translation codes, the code threading them through was correct and a raw INSERT in a different function still named only the original columns. Every code would have been computed perfectly and then silently dropped on the way into the database. The same gap existed separately in the manual-confirmation path. Both are now pinned by tests that read the evidence back through the real database — because a correct struct is not the same thing as correct bytes on disk.

Missions and agents are linked

A mission knows which agent sessions worked on it, and a session knows which mission it serves. That link is what makes the thread readable end to end: mission → agent → terminal → conversation → evidence. Mission Control is built on it, and so is the unattended run, where the autopilot takes the human's seat and verifies after every turn.
