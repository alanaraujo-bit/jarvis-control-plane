Um agente que diz Pronto! te contou no que ele acredita. Uma missão é o mecanismo para descobrir se é verdade — e para perceber depois quando deixa de ser.

Do que uma missão é feita

Um título e uma intenção
O que você quer. Prosa comum, nas suas palavras.
Critérios de aceitação
As condições que decidem se está terminada. Cada um é obrigatório ou não, e cada um carrega uma verificação — a coisa que vai de fato ser executada.
Um perfil de autonomia
Quanto o agente decide sozinho. Veja Autonomia.
Evidência
O que cada checagem produziu, guardado — não um tique verde, o resultado de fato.

Os quatro tipos de verificação

TipoO que fazConferido por
Command Roda um comando e compara o código de saída com o que você esperava (0, a menos que diga outro). Roda no diretório do projeto, salvo se receber outro. J.A.R.V.I.S.
FileExists Um caminho, relativo ao projeto, tem que estar lá. J.A.R.V.I.S.
FileContains Um caminho tem que estar lá e conter o texto informado. J.A.R.V.I.S.
Manual Só uma pessoa consegue julgar. Registrado como tal, para nunca ser confundido com algo que foi realmente conferido. Você
A razão de existir do quarto

Manual existe para que "a tela de login está com a cara certa" possa ser um critério de verdade sem fingir que uma máquina verificou. A evidência dele lê confirmado por você, nunca passou. Um critério que não pode ser conferido só pode ser alegado, e o produto se recusa a embaçar os dois.

Os sete estados, e por que dois deles existem

Esperando e Bloqueada são os dois que a maioria das ferramentas não tem, e são a razão pela qual este modelo vale alguma coisa. Uma missão que não consegue prosseguir tem que dizer isso. As alternativas são declarar sucesso caladinha, ou queimar seus tokens para sempre — e as duas são coisas que um agente faz com prazer se o modelo não deixar outro lugar para ele ir.

Uma missão bloqueada também tem que se explicar. Bloqueada sem motivo é um estado sobre o qual ninguém consegue agir.

A conclusão é recusada, não pedida

Você não consegue marcar uma missão como concluída porque acha que ela está. As checagens rodam; se um critério obrigatório não se sustenta, a conclusão é recusada e a superfície diz qual e por quê.

Verificado no produto real

Uma missão foi criada, a conclusão foi recusada, a verificação rodou, o trabalho foi feito, a verificação passou, e a missão concluiu. Aí o artefato foi apagado do disco e a conclusão foi revogada — porque a evidência parou de se sustentar.

A revogação é a parte que as pessoas não esperam

A evidência é reconferida, e uma conclusão cuja evidência não se sustenta mais não continua concluída. É isso que faz uma missão ser diferente de um checkbox: um checkbox registra que alguém um dia acreditou em alguma coisa. Uma missão registra se ela é hoje verdade.

Retirar um critério é registrado, nunca apagado

Se um critério se revela o pedido errado, você o retira — com um motivo. Ele fica no registro, marcado como retirado, com o seu motivo anexado. Apagar deixaria uma missão passar pela remoção dos testes que ela falhou, que é exatamente a manobra que este modelo todo existe para impedir.

Como a evidência se parece

Toda frase que o J.A.R.V.I.S. escreve como evidência é uma string traduzida com os detalhes substituídos dentro, e não texto em inglês guardado no seu banco. Um comando que falha lê, exatamente:

`exit 1` saiu com código 1, esperado 0

A saída do próprio comando — stdout, stderr, uma string de erro do sistema operacional — é guardada sem código de tradução nenhum, deliberadamente. Ali é a ferramenta falando, não uma frase que o J.A.R.V.I.S. escreveu, e traduzir seria inventar palavras que ninguém disse.

Um bug que vale conhecer

Quando a evidência ganhou seus códigos de tradução, o código que os conduzia estava correto e um INSERT cru em outra função continuava nomeando só as colunas originais. Todo código teria sido calculado perfeitamente e depois descartado em silêncio no caminho para o banco. A mesma brecha existia separadamente no caminho da confirmação manual. Os dois agora são fixados por testes que leem a evidência de volta pelo banco de dados real — porque uma struct correta não é a mesma coisa que bytes corretos em disco.

Missões e agentes são ligados

Uma missão sabe quais sessões de agente trabalharam nela, e uma sessão sabe qual missão ela serve. Esse vínculo é o que torna o fio legível de ponta a ponta: missão → agente → terminal → conversa → evidência. A Central de Missões é construída em cima dele, e a execução sem supervisão também, onde o piloto automático assume a cadeira da pessoa e verifica depois de cada turno.

No código

mission/model.rs é a máquina de estados e os tipos de verificação; mission/verify.rs roda as checagens reais e escreve a evidência; mission/store.rs é a persistência.
