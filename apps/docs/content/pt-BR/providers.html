Três provedores vêm dentro do J.A.R.V.I.S. hoje: Claude Code, Codex e o Local — um modelo rodando na GPU desta máquina. Eles não são intercambiáveis, e fingir o contrário seria o jeito mais fácil de fazer a interface mentir.

O terceiro é a prova de que esse desenho funciona. Ele chegou sem remodelar nada acima dele: nenhum arquivo React aprendeu um caso especial novo, porque a interface é renderizada a partir do que os adaptadores declaram, e não de booleanos escritos dentro de componentes. O que ele precisou foram três respostas novas e honestas — ele não tem conta, o suporte a imagem é assunto do modelo carregado e não do adaptador, e ele escreve os transcripts num lugar em que só ele escreve.

Um provedor é um adaptador, não um caso especial

Cada provedor é um adaptador em Rust por trás de um único trait. A primeira função do adaptador é se descrever, devolvendo uma struct ProviderCapabilities — como as sessões são correlacionadas, de onde vem a conversa, se o uso é oficial, se uma operação sensível pode ser parada, como um briefing chega até ele, de onde as sessões dele tiram nome.

A regra

Capacidades são dados. Elas nunca são um booleano escrito dentro de um componente. Uma superfície renderiza a partir do que o adaptador informa. Adicionar um terceiro provedor não pode exigir encostar em um único arquivo React — e se exigisse, a abstração já teria falhado.

Isso soa como boa prática comum até você ver o custo de quebrá-la. A alternativa é um componente que diz if (provider === "claude-code"), que está correto no dia em que foi escrito e silenciosamente errado para todo provedor adicionado depois. Existe um teste que falha se os dois adaptadores algum dia se descreverem de forma idêntica, porque dois provedores informando as mesmas capacidades é muito mais provável de ser um copiar-e-colar do que uma verdade.

Correlação: qual transcrição pertence a esta sessão

Quando você inicia um agente, o J.A.R.V.I.S. precisa saber qual arquivo JSONL no disco é o que este processo está escrevendo. Errar isso atribui o trabalho de um agente a outro.

O Claude Code aceita --session-id <uuid> e escreve a transcrição dele com esse nome. O vínculo é um fato que nós afirmamos, então é Deterministic.

O Codex nomeia os próprios arquivos de rollout. O adaptador observa o diretório e casa com o arquivo que apareceu depois que este processo começou. Isso é uma heurística muito boa e continua sendo uma heurística, então é informado como FileWatch em vez de enfeitado. Duas sessões do Codex iniciadas no mesmo segundo na mesma pasta é o caso em que ela poderia errar, e dizer isso é mais barato do que estar confiantemente enganado.

Proteções: parado, ou só observado

As duas CLIs têm um hook pré-ferramenta com o mesmo formato de fio. O Claude Code executa ele: uma recusa realmente para o comando antes de ele rodar, verificado contra a 2.1.240 recusando um push forçado real e confirmando que o remoto ficou intocado.

O Codex não executa um hook até você ter revisado e confiado nele na interface do próprio Codex. O J.A.R.V.I.S. escreve a configuração do hook no início da sessão para que ela esteja lá para ser confiada, e até você fazer isso aquela sessão é observada e não protegida. É exatamente isso que PreExecutionWhenTrusted quer dizer, e a interface fala isso em vez de te mostrar um escudo que não está fazendo nada.

Briefing: como a memória do projeto chega ao agente

A Memória entrega um briefing a todo agente antes de ele começar. O Claude Code aceita --append-system-prompt-file, então o briefing é passado fora de banda: nada é escrito no seu repositório, nada é gasto de um turno, e nada aparece no terminal.

O Codex 0.147.0 não tem flag equivalente. Um briefing só poderia chegar como a mensagem de abertura da sessão — visível, e custando um turno. O adaptador informa OpeningMessage, e uma pessoa escolhendo provedor para uma execução sem supervisão consegue ver qual das duas está levando.

Medido, não lido de uma página de ajuda

A capacidade de briefing do Claude Code é fixada por um teste marcado #[ignore] que inicia um agente real através de um PTY real e pede um codinome que só aparece no briefing. Com a flag ele responde; sem ela, não. Uma capacidade afirmada a partir de uma listagem de --help é uma afirmação sobre documentação, não sobre comportamento.

Títulos: quem dá nome a uma sessão

O Claude Code escreve uma linha ai-title na própria transcrição. Nada estava lendo isso, então toda sessão no banco ficava sem título até o Histórico ser construído. Ela está presente em 89 das 124 transcrições da máquina em que isso foi verificado.

O Codex não declara título em lugar nenhum. set_thread_title existe nos rollouts dele, mas como definição de ferramenta dentro das instruções, e não como um evento que ele emite — conferido em todos os rollouts daquela máquina. Então as sessões dele ganham um título Derived, calculado a partir do que foi dito nelas.

Os dois são observados do mesmo jeito

A pergunta que decidiu todo este desenho foi se uma sessão pode estar simultaneamente presa a um PTY e ser observável estruturalmente. Pode: as duas CLIs escrevem transcrições JSONL estruturadas em disco enquanto rodam interativamente.

// Claude Code
~/.claude/projects/<cwd-codificado>/<session-uuid>.jsonl
  eventos user · assistant · system · attachment · ai-title · file-history-*
  uso     assistant.message.usage → input, output, cache_creation, cache_read
  forma   as mensagens formam um DAG via parentUuid

// Codex
~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl
  envelope {timestamp, ordinal, type, payload} — ordenado estritamente por ordinal
  tipos    session_meta · event_msg/* · response_item/* · turn_context · world_state
  uso      event_msg/token_count carrega rate_limits oficiais

É por isso que a Conversa é dado estruturado de verdade, e não ANSI raspado de um terminal. O leitor que acompanha esses arquivos lida com linhas parciais, sequências UTF-8 partidas entre leituras, truncamento e CRLF — e foi validado analisando toda transcrição real da máquina de desenvolvimento: 79 arquivos, 49.905 itens de conversa, 19.582 deles carregando uso oficial.

Onde um provedor é escolhido

Na área Sessões de um projeto, o + ao lado da faixa de abas oferece um Shell simples e todo agente que a varredura de ambiente encontrou na sua máquina. Um provedor cujo executável não está no PATH não é oferecido, e a seção Ambiente das Configurações diz o que está faltando.

No código

providers/mod.rs é o trait e o modelo de capacidades; providers/claude.rs, providers/codex.rs e providers/local.rs são os adaptadores, cada um com o raciocínio dos próprios valores em comentários; localai/ é o runtime local a partir do qual o terceiro é configurado; providers/tail.rs é o leitor de JSONL.
