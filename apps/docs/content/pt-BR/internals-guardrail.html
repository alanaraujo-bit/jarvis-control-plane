Como um comando é parado antes de rodar, e por que o mecanismo tem o formato que tem. O detalhe de comportamento está em Proteções; esta página é a maquinaria.

O pipeline

Por que a guarda é um processo separado

Porque uma sessão tem exatamente um escritor

A guarda roda como processo próprio e nunca pode ser a escritora do log. Ela entrega as decisões dela do mesmo jeito que um provedor entrega a transcrição: anexando a um arquivo que o escritor único acompanha e transforma em quadros Approval.

Este é o mesmo formato de dois processos que toda a arquitetura usa, e é o que mantém a ordem no log como um fato em vez de um acordo entre escritores concorrentes.

O provedor invoca ela — o mesmo executável, com uma flag — antes de toda chamada de ferramenta classificada. Ela lê o snapshot, classifica o comando, e responde na saída padrão.

Por que é um snapshot, e não uma leitura ao vivo

O guardrail-policy.json é escrito quando a sessão começa, carregando as regras já resolvidas pela cadeia projeto → global → padrão e se alguém está presente.

Mudar uma regra nas Configurações no meio da sessão não deveria mudar o que um agente em execução recebeu. Uma sessão que começou sob uma política termina sob ela, o que também é o que torna o registro legível depois: as decisões no log são decisões sob uma política que você consegue inspecionar.

Por que ela falha aberta

Sem snapshot, JSON malformado, ou uma versão que ela não entende: ela fica em silêncio e a chamada de ferramenta prossegue.

Faça a conta do raio de alcance

Este processo roda antes de toda chamada de ferramenta em toda sessão de agente. Uma guarda que falhasse fechada transformaria qualquer bug nela mesma — um arquivo faltando, um erro de parse, uma diferença de versão depois de uma atualização — em um agente que não consegue fazer absolutamente nada, em todo projeto, até alguém diagnosticar.

Falhar aberta faz um bug te custar a proteção. Falhar fechada faz um bug te custar o produto.

O classificador

Casamento heurístico sobre o texto do comando. Ele tokeniza, respeita aspas, e lê cada programa com os argumentos dele. Ele não é um parser de shell e não finge ser — um parser de shell de verdade teria que lidar com toda expansão, substituição e alias, e seria uma superfície bem maior para errar sutilmente.

Os casos negativos são os que sustentam tudo

Se o classificador sinaliza coisas que não deveria, ele vira a primeira coisa que qualquer um desliga — e aí ele não protege nada. Então estes são fixados por testes:

✓ não casa  git push --force-with-lease origin main
            se recusa sozinho quando o remoto mudou — a grafia segura
✓ não casa  echo "rm -rf /tmp/x"
            uma string sendo impressa, não um diretório sendo apagado
✓ não casa  npm publish --dry-run
✓ não casa  cat .env.example
✓ não casa  git switch main
            mas `git switch --discard-changes main` casa

✗ casa      pnpm build && git push --force && npm publish
            cada parte de uma cadeia é classificada separadamente
Não sinalizado não é provado seguro

Um comando que o classificador não sinaliza falhou em casar com um padrão. Essa é uma afirmação diferente de isto é inofensivo, e só uma delas é verdadeira.

Os identificadores são estáveis e nunca são prosa

As nove operações têm identificadores fixos em string — git.force-push, fs.recursive-delete, secrets.access e assim por diante. Eles são usados no armazenamento, no snapshot de política, e como sufixo de chave para o nome traduzido. Um nome que um usuário lê nunca é a coisa que um banco de dados guarda.

A aplicação difere por provedor, e o modelo diz isso

O Claude Code executa o hook e uma recusa realmente para o comando. O Codex tem o mesmo mecanismo de hook mas não executa ele até você ter confiado na interface do próprio Codex, então ele é informado como PreExecutionWhenTrusted — observado, não protegido, até você fazer isso. Veja a matriz de provedores.

Onde a trava não é um classificador

Dentro da Revisão, um descarte nomeia a operação dele diretamente em vez de montar uma string de comando e perguntar ao classificador o que ele acabou de decidir fazer. Ele também não escreve linha pendente nenhuma: você está na tela, então a pergunta é feita e respondida ali em vez de virar algo para resolver depois.

Classificar uma string que você mesmo acabou de construir é uma ida e volta por uma heurística para recuperar informação que você já tinha.

Em Sem supervisão

O snapshot carrega se a sessão é dirigida. Uma sessão dirigida com uma regra em perguntar recebe uma recusa, porque estacionar o agente num prompt que ninguém vai responder desperdiça a execução inteira. A missão vai para Esperando com um motivo.
